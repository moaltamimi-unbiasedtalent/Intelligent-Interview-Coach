## 13 to 15. Usage quotas, PostgreSQL concurrency and reservation recovery
P4-A SQLite tests are now complemented by execution on an **isolated PostgreSQL 16.14 server** (throwaway cluster in a temp directory, loopback port, never a developer database; the test guard refuses any other PostgreSQL URL). Results (`tests/test_pg_p5b.py`, two clean runs, then once inside the full suite): 8 OS processes x 12 attempts (96) against an allowance of 25: 25 approved, 71 denied, 0 database errors, final counter 25, reservation states committed 13-15 and reserved 10-12 across runs, the other candidate's counter 0; 6 processes x 5 identical operation keys: exactly 5 reservations and 5 units; 16 threads across a UTC hour boundary: exactly 4 approved per hour (never 5), a denial leaves no reservation row, explicit release returns a unit once, reaping returns the rest. **Defect found and fixed:** a reservation is released after 15 minutes without renewal, so a running operation longer than that would have been released while still running. Correction: a lease heartbeat (`src/application/lease.py`) renews a held reservation from the `ai_operation` dependency; tests (SQLite and PostgreSQL) show a renewed reservation survives past its lease while a crashed one is recovered, a late commit for a recovered reservation is refused, and a finalized reservation is never renewed. Policy: a quota-store failure fails closed for the gated operation (503); an unconfirmed reaper is not scheduled yet (operational dependency); numerical allowances and activation remain unapproved. Not covered: a PostgreSQL run with several separate application instances behind a load balancer.

## 19. Employer-specific personalization
Finding: P5-A had removed the employer name from the model context, so two Packs for the same role at different employers produced identical model context. Correction: the employer NAME (opportunity-provided) is context again, inside the untrusted data block, with an explicit system rule that nothing about the employer may be stated beyond the requirements; no retrieved company fact, excerpt or source is ever put in the context. This is contract evidence only: whether live output is actually better personalized was NOT measured (no live provider evaluation).

## 20. Unsupported-claim filter evaluation
A deterministic labelled set of 26 sentences (`LABELLED` in the P5-B test): 17 that must be blocked and 9 legitimate. Measured: 13 true positives, 4 false negatives, 0 false positives (counting 2 intentionally conservative rejections of unsupported years or figures as true rejections), 9 true negatives. No accuracy percentage is claimed beyond these counts. **Defect found and fixed by this evaluation:** the percentage pattern ended in a word boundary after "%", so "35%" was missed whenever a space or full stop followed; fixed with a regression test. **Improvement without loosening:** a figure that appears in the candidate's own job description, claims or stories may be echoed; money, compensation words and URLs are never excused. The four false negatives are qualitative or unlisted-wording claims ("Median market pay is high", "market leader in Europe", "no-layoff policy", an invented CEO history): the lexical filter cannot judge qualitative falsehoods, and no semantic verification is claimed; such text stays labelled as AI guidance with no citation.

## 21 and 23. Long-running Pack generation and revision integrity
Finding: the P5-A lease was renewed only between stages, so one blocking stage longer than 15 minutes could have been recovered while the worker was alive and replaced by a second generation. Correction: a heartbeat thread renews the lease for the whole generation (`Heartbeat`); recovery means 15 minutes of silence; finalization is single-use so a stale worker is fenced out. Also found: the stage-boundary renewals were unguarded and a failing renewal failed a healthy generation; they are now swallowed. Accelerated-clock tests (lease shortened to 1 second): one 3-second blocking stage is kept alive and a concurrent request gets `in_progress` with one provider call; a dead worker is recovered, a new generation proceeds and the stale result is refused; every renewal failing does not kill a healthy generation; five sequential generations give revisions 1 to 5. PostgreSQL: 6 processes x 6 start attempts gave unique contiguous revisions and no database error (created 6-13, the rest `in_progress`). Not covered: a worker whose database connection is dead for longer than the lease is recovered by design.

## 22. Pack migration on PostgreSQL
Executed on the isolated server (not only rendered): `0034_preparation_packs` creates the partial unique index (`... WHERE status = 'generating'`), the revision constraint, cascade on user delete and SET NULL on opportunity delete; one-step downgrade and re-upgrade are clean; duplicate op key, duplicate revision, bad status and a second generating row are rejected; different opportunities or users may generate concurrently; NULL opportunity rows are distinct under PostgreSQL (the constraints do not bind them; generation requires a live opportunity). **Defects found by running the full chain on a fresh PostgreSQL database and fixed (all invisible on SQLite):** (1) revision ids longer than 32 characters overflow Alembic's default `alembic_version` column, so `alembic upgrade head` failed at revision 0004 on a fresh server; `migrations/env.py` now widens the column first (`src/db_migration_support.py`); (2) five BOOLEAN columns had numeric defaults (`DEFAULT 0`) in migrations 0007, 0020, 0023, 0029, 0031; now `sa.false()`; (3) two CHECK constraints compared a BOOLEAN to `1` (migration 0016 and the model, 0020 and the model); now portable boolean tests. `deploy/scripts/migrate.sh` documents `alembic upgrade head` on PostgreSQL as the deployment path, so these were operational defects. The edits change no SQLite behaviour, and a server-free test pins all three.
