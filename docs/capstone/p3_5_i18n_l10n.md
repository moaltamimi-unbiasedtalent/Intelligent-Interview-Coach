# P3.5 — Internationalization & Localization Foundation (7-language product)

Capstone implementation story. Establishes internationalization/localization as a formal
product capability across seven candidate languages, with three **independent** language
concerns, without changing the agent's intelligence, retrieval geography, grounding,
HITL, identity, security, the P2 response experience or the P3 dictation feature.

Base: `main` @ `9ed55c4` (P3 merged, PR #76). Branch: `feature/capstone-p3-5-i18n-l10n`.
No historical tag moved.

## What
A version-controlled, typed catalogue system with a locale registry, English source +
fallback, cookie/account preference resolution, locale-aware formatting, and three
distinct language controls: **interface**, **Mo conversation**, and **dictation**.

## Why / commercial rationale
Ask4Mo targets candidates across European markets. Language accessibility is
commercially important and must be **distinct from labour-market geography**: a
candidate may use a German interface, speak English into dictation, and want Mo to coach
in English while preparing for a role in the UK market. Collapsing these into one
"Language" setting would break real use cases.

## Architecture (library/approach + why)
**Chosen: a lightweight, typed, catalogue-based i18n with cookie + account-preference
resolution and a React context provider — no `[locale]` routing.**
- **App Router compatibility:** works with the existing flat route tree; no restructure
  into `app/[locale]/**` and no rewrite of every `Link`/route/e2e.
- **Server + client:** the server layout reads the locale cookie to set the initial
  `<html lang>`; a client `I18nProvider` resolves the authoritative locale and exposes
  `t()` + formatters to all client components.
- **Type-safety:** English (`messages/en.ts`) is the reference; the `Catalog` type
  gives every other locale the **exact** same keys (compile-time parity).
- **Fallback:** missing key → English → the key string (never `undefined`/blank).
- **Bundle/testing:** no new runtime dependency; catalogues are plain modules; a
  deterministic fake/override is trivial in tests.
- **Why not next-intl:** considered, but its idiomatic setup uses a `[locale]` routing
  segment + middleware, forcing a high-risk restructure of every route inconsistent with
  the "preserve architecture" mandate. Preference/cookie resolution is explicitly
  permitted by the phase brief and is the lower-complexity, safer fit here.

## Locale registry & catalogues
`lib/i18n/locales.ts` — `APP_LOCALES` (en, de, fr, es, it, pt, nl) with native labels,
`toSupportedLocale()` (narrows unknown → null). `lib/i18n/messages/<locale>.ts` — one
catalogue per language, each typed `Catalog`. `lib/i18n/catalog.ts` — assembly +
`translate(locale, key, vars)` with English fallback and `{var}` interpolation.

## Preference model
- **interface_locale** and **conversation_language** are server-persisted on
  `user_preferences` (migration 0009), independent of each other, of the model profile,
  and of the P3 dictation locale. Both default to English; both bounded to the seven
  codes (a spoofed value → 422). Exposed on `AccountResponse`; updated via the existing
  partial `PATCH /auth/preferences`.
- **Anonymous/first-use:** a non-sensitive `ask4mo_locale` cookie (+ browser-locale hint).
  After sign-in the account preference is authoritative and survives logout/login and
  devices. localStorage is never the sole authenticated source.

## Interface vs dictation vs Mo conversation language (kept independent)
Settings shows three separate controls (`components/settings/LanguageSettings.tsx`):
Interface language (drives the UI + `<html lang>`), Mo conversation language (persisted;
plumbed to the agent), Dictation language (P3 per-device BCP-47). One never silently
changes another.

## Mo conversation language (implementation + honest status)
The agent request carries a bounded `conversation_language` (`Literal` of 7 codes). The
service validates it against an allow-list (`_resolve_language`) into a new
`response_language` state field. The `initialise` node appends a **single, allow-listed**
directive ("Respond in <language>…") built only from `RESPONSE_LANGUAGE_NAMES` — the raw
code never reaches the model, so it cannot inject prompt text; English adds no directive.
The directive explicitly instructs Mo not to change geography. Tool selection, retrieval,
grounding and the bounded step budget are unchanged; `eval_agent` GATE PASS is preserved.
**Live multilingual response quality is UNVALIDATED** (no paid run this phase) — the
plumbing and safety are deterministically tested.

## Routing / fallback
No locale in the URL; locale is resolved from account → cookie → browser → English.
Missing translations fall back to English; unknown locales narrow to English.

## Language ≠ geography (safety)
Proven: retrieval geography is `detect_country(query text)` (`src/copilot/knowledge/
router.py`) — a pure function of the question, with no language parameter. No agent or
copilot code derives geography from language. Regression tests
(`tests/test_conversation_language.py`) assert `detect_country` stability and that the
directive text forbids changing geography.

## Accessibility
`<html lang>` is set server-side from the cookie and kept in sync client-side on locale
change. Localized labels flow through existing accessible controls (nav, account, auth,
settings, language selectors). German/French (longer strings) render without clipping in
the localized surfaces; verified in the locale e2e smoke.

## Privacy / legal boundary
Language preferences are low-sensitivity metadata (never candidate content). Translated
privacy/help text improves usability but is **not** legally validated by existing in
another language. All translations are labelled **ENGINEERING DRAFT**; none is claimed as
human- or legally-reviewed (see the review matrix). Policy translations requiring counsel
are flagged for pre-launch review.

## Testing / evaluation
- Frontend `tests/i18n.test.tsx` (11): registry, **exact key parity across all 7
  locales**, no-blank values, fallback, interpolation, unsupported-locale safety,
  provider switching (German), independent conversation control.
- Backend `tests/test_locale_preferences.py` (6) + `tests/test_conversation_language.py`
  (7): persistence, isolation, partial update, bounded rejection, prod fail-closed,
  allow-listed injection-safe directive, geography independence.
- `e2e/i18n.spec.ts` (8): 7-language nav switch + `<html lang>` + three-control settings.
- `scripts/eval_i18n_l10n.py`: all invariants PASS (registry, completeness, fallback,
  unsupported safety, route/lang handling, preference persistence, cross-user isolation,
  language/geography separation, injection-safe directive, dictation/conversation
  separation). Wired into CI.

## Coverage (honest)
- **Fully localized (7 languages, engineering draft):** app shell/navigation, account
  menu, sign-in, settings (incl. the three language controls + response detail), home
  hero + return journey, dictation control labels/status/errors, and the catalogue keys
  for help section titles, common states and validation/auth messages.
- **PARTIAL (architecture ready; strings migrate incrementally):** deep per-page strings
  in Prepare/Practice/Deep-Dive/Report/Progress/History/Sources, the full Help article
  corpus (section titles are catalogued; bodies remain English), and the guided tutorial
  step text. These render correctly (English) and adopt the same catalogue as their
  strings are extracted under the new coding standard.
- **English-only by design:** reviewer/diagnostic surfaces (Agent Inspector, RAG/eval
  diagnostics) per §9.

## Known limitations
Engineering-draft translations (not human/legal reviewed); live multilingual Mo quality
UNVALIDATED; Help bodies + tutorial + deep pages are incremental; RTL intentionally not
implemented (LTR-only scope) but the architecture does not preclude it.

## Future marketing / admin integration
The future public marketing site (P8) and any localized admin surfaces reuse **this**
catalogue system (add namespaces + routes) — no second i18n system. Admin Console
localization is **optional** for first commercial launch (platform admin can remain
English initially).

## Coding standard (from now on)
New candidate-facing user-visible strings MUST use the i18n system (add a key to the
English catalogue + all locales). Recorded in `CLAUDE.md`. Reviewer-only debugging text
is exempt.

## Lessons learned
Internationalization is an **architectural** concern, not a final copy-editing pass:
separating interface/conversation/dictation language and proving language≠geography were
the load-bearing decisions; the catalogue + fallback made the whole thing testable and
kept English behaviour (and every existing test) unchanged.
