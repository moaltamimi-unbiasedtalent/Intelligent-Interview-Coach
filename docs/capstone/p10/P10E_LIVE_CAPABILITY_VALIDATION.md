## 2. Mandatory safeguards (implemented and tested before the first paid request)
**A. The execution flag is enforced.** `require_live` refuses unless `paid_execution_enabled` is the boolean `true`: missing, null, `false`, the strings `"true"`, `"True"`, `"yes"`, `"1"`, the number 1 and empty containers are all refused (10 cases tested). The owner checks (grant, approval metadata, all seven limits listed as approved and valid, spend not above USD 10) and the flag are independent: neither bypasses the other. P10E_LIVE=1 is mandatory per run, CI is refused, and a CI workflow contains none of these names (tested).
**B. The cumulative budget is persistent and protected** (`src/p10e/ledger.py`). One SQLite ledger (`synchronous=FULL`, so a reservation is on disk before a request is sent) in a directory configured explicitly through `P10E_LEDGER_DIR` (no default; nothing is created by a refusal), outside every Git checkout, owned by the running user and closed to group and others (directory 0700, file 0600). It is append-only by construction: triggers refuse DELETE and refuse changing a settled entry, any identity column, the approved total or the genesis; reservations are hash-chained with a recorded head, so alteration, removal, reordering or tail truncation is detected when the ledger is opened (5 tamper scenarios tested, each refused). **Identity:** a genesis id, the environment id and a host fingerprint are bound into the ledger; the reviewed authorization records the expected genesis id, so a new empty ledger in another checkout or location can neither be initialized (a second `ledger-init` is refused) nor accepted (genesis mismatch), a copied ledger on another host is refused, and a missing ledger after use is a STOP, never an automatic re-initialization. **Exclusive session:** an operating-system `flock` held for the whole session (an in-process second session and a competing process are both refused; the OS releases it if the process dies, so there is no stale lock to break). **Crash safety:** a reservation is committed before the request is sent; a session that did not close cleanly is reconciled under the lock and every reservation it left open is kept at its FULL worst case (a hard-killed process test shows the USD 4 reservation still counts and the same USD 6.5 request is refused). Nothing is ever refunded, reset or deleted.
**The chokepoint** (`src/p10e/httpguard.py`). Every provider request in Ask4Mo (the OpenAI SDK behind LangChain, nested agent calls, helper agents, SDK retries) passes through `httpx`; during a session the guard wraps `httpx.Client.send` and `AsyncClient.send` so that no request is sent unless: the host is `openrouter.ai`, the endpoint is the priced chat endpoint (read-only metadata endpoints are allowed and never billed; embeddings and everything else are refused), the model has a published price, streaming is off, the outgoing body carries an output cap at or below 2,000 (`max_completion_tokens`, which is what the real SDK sends), the SDK retry counter is within the approved retries, the pessimistic input estimate (messages, tools, response format) fits 20,000, and the ledger accepts the worst-case dollar and call reservation, committed durably first. Concurrency is bounded by a semaphore, the timeout is clamped to 60 s, each SDK retry is its own reserved and counted request, a determinate provider rejection (400, 401, 402, 403, 404, 422, 429) releases the dollars but keeps the call counted, a response with usage is priced from the reported tokens (the larger of the calculated and provider-reported figure), and a timeout, connection loss, server error or missing usage keeps the full worst case. These were tested with the real OpenAI SDK over a mock transport (no network).
**Designated environment:** `p10e-designated-host-owner-macos` (this host, bound by fingerprint); ledger at `$HOME/.ask4mo/p10e-ledger`; permitted runner: the owner's macOS account; locking `flock`; persistence SQLite with the protections above; a consistent backup copy is written at each clean close; recovery: a missing, corrupted, wrong-host or mismatched ledger stops execution and must be restored or reconciled by the owner (restoring a backup older than the last session would understate spending and must first be reconciled against the per-run evidence and the provider snapshots). A local lock cannot protect a different host; the procedure is a single designated host, enforced by the fingerprint.
**Tests:** 81 P10E tests (`tests/test_p10e_live_guard.py`, `tests/test_p10e_ledger.py`) including cross-run USD 10 and 300-call enforcement, two sequential sessions with restart, a second checkout, a missing and a corrupted ledger, a killed process, concurrent admissions, retry accounting, settlement rules, the USD 15 attempt, the oversized, unpriced, streaming and other-host requests (none reaches the transport), and the runners. Testing found and fixed two real defects before any live call: the SQLite connection was bound to its creating thread (the SDK and agents can call from worker threads) and admission refusals were not recorded where the runners look for them.

## 9. Findings and accepted limitations
1. The environment's effective profile models differ from the registry code defaults, and the agent path keeps a helper pinned to the code default slug (product inconsistency, reported).
2. The approved 2,000 output-token cap blocks the product's 4,096-token structured tools: 5 of 22 agent cases (more with Fast and Advanced) cannot be evaluated. A separate owner approval would be needed to raise `max_output_tokens_per_request`; it was not requested and not changed.
3. The credential is shared and has a provider-side limit; the ledger cannot control unrelated spending.
4. A 5.5% unexplained difference between per-request provider-reported costs and the account-level delta.
5. Small samples, no acceptance thresholds, human-rated metrics pending, no native-language review, results on synthetic fixtures only.
6. Interview quality, semantic retrieval, RAGAS and multilingual live are NOT RUN.
