## 4. Multilingual alias model (PROPOSED DESIGN; QUALIFIED IMPLEMENTATION)
Table `graph_occupation_aliases`: canonical occupation, original `alias_text` (never replaced), `normalized_text`, `folded_text`, `normalization_version`, language (`und` = unknown), `language_basis` (unknown, source_declared, source_file, fixture_declared, curated_manual), script (ISO 15924, derived), alias type (official_preferred, official_alternative, source_synonym, recognized_title, legacy_alias, unknown), source reference, taxonomy edition (explicit, or empty), qualification status, status, curated `context_terms`, provenance, validity metadata.
Rules (service-validated, and database CHECKs where possible): an unknown language carries basis unknown and a known language must name its basis (never guessed); an official type needs a registered source with a known origin; a new alias is always `unqualified`; `qualified` needs a named reviewer and a non-fixture, known-origin source and is audited in the provenance history; synthetic-fixture aliases are stored but never evidence-eligible.
Uniqueness is per (occupation, normalized text, language, type, source, edition), so two occupations may share an alias (this produces AMBIGUOUS), one occupation may hold several aliases per language, and an alias may differ by edition; nothing forces distinct occupations to merge. Shared aliases and same-source official-label conflicts are reported explicitly.

## 5. Language support (QUALIFIED IMPLEMENTATION)
Table `language_coverage` keeps five facts separate per language: UI supported, taxonomy supported, alias data available, alias qualified, resolver supported. Languages are any well-formed identifier, independent of the eight UI locales. Seeded: en (taxonomy and alias data available; legacy aliases unqualified, not yet in the graph), de (taxonomy available through KldB; alias data only source-identified), fr, es, it, pt, nl, ru (targeted only; no source identified or acquired; ESCO language availability and licence unverified). **Russian is a UI locale only; no official Russian occupation source is assumed.** `resolver_level = implemented` means deterministic normalization is applied and exercised on synthetic fixtures, not qualified alias data. Nothing is qualified; the table has no country column.

## 6. Normalization (PROPOSED DESIGN `n1`)
Exact key: NFKC, case folding, punctuation/hyphens/slashes to a space, whitespace collapsed; diacritics kept; `+ # &` and a leading or inner `.` kept (`C++`, `C#`, `.NET`, `Node.js`). Tolerant key: combining marks removed for Latin tokens only; Cyrillic and Greek never folded (Russian `й` is not folded to `и`). Not done: transliteration, compound splitting, gender-form or abbreviation expansion, stemming, translation. Locale-independent case folding (`ß` to `ss`; Turkish dotted i not special-cased: limitation). Regression tests cover `año/ano`, `майор/маиор`, `C/C++/C#`, compounds and hyphenation.

## 7. Multilingual ESCO integration (GKB-4)
`esco_adapter.py`: version-aware (edition explicit), language explicit (from the caller; for a file, from `occupations_<language>.csv`), ISCO digits kept as strings. `plan_esco_labels` is read-only and needs no approval (assessment, not import): for the local English file it matches all 3,039 occupations and sees 33,518 labels. Persisting goes only through the registry: **production mode needs `can_ingest(source)`** (approved for ingestion, verified licence, non-fixture origin); **fixture mode needs a synthetic-fixture source** and stores labels that are never evidence. One transaction, idempotent, labels attach only to existing ESCO nodes. **Today the `esco` source is LICENSING PENDING, so a production import is refused; no other language file exists locally.** Unavailable and documented: any non-English ESCO release, any German or other alias data, source approval.

## 9. Taxonomy editions
Editions stay separate namespaces; an alias may name its edition; an edition-specific alias is excluded for another or unknown edition; unknown is not compatible. Tightening found by the fixture corpus: the default identity of esco/isco/soc/onet/kldb nodes ignores the edition (it preserves legacy ids), so registering ISCO-88 `9912` could silently merge into the ISCO-08 node. `add_occupation` now gives a default registration its own edition-aware identity when the owning node already holds the scheme in another edition (explicit keys unchanged). Cross-edition identity requires a stated relationship.

## 10. ISCO leading zeros
Codes are strings. Official ISCO-08 identity is the padded code (`0110`, `0210`, `0310`); the stripped legacy value stays a legacy key. `restore_isco_zero_padding` restores padding only when the stripped value is not itself an official code, exactly one padded variant exists in the authority and the variant is in major group 0; otherwise it reports `not_found`, `ambiguous_padding` or `invalid_format` and never invents. The resolver surfaces `isco_zero_padding_restored:110->0110` and the grade `code_zero_padding_restored`. All 21 legacy mappings (7 each for 110, 210, 310) are covered by a synthetic reproduction of the real shape; the real-store assessment (3,018 exact, 21 lost a leading zero, 0 mismatches) is the P10C-A result and the real store was not rewritten.

## 11. Crosswalk qualification
`qualification.py` asks five distinct questions of every relationship: structurally valid, source linked, official source provided, independently reviewed (status `qualified`, a named human review), licensed for runtime (`can_serve_as_evidence`). `operationally_approved` needs official source, review, runtime licence and VERIFIED status. Applied to the P10C-A graph: the 3,039 ESCO-to-ISCO relationships are structurally valid, source-linked and official-source-provided (the `esco` source has an official local origin) but **not independently reviewed and not licensed for runtime**, hence not operational; VERIFIED means the official file states them and the code exists, nothing more. Relationships against synthetic fixtures never exceed `source_linked`.

## 12. Resolver (GKB-13; PROPOSED DESIGN; INTERNAL)
`occupation_resolver.py`. Inputs: title, `title_language` (language OF THE INPUT TEXT; there is no interface-locale field), country (explicit), taxonomy scheme/code/edition, role context, industry, seniority, known keys, and two explicit opt-ins (`allow_cross_language`, `accept_unverified_language`). Evidence ladder: known key, exact code (edition-explicit, ISCO restoration), exact alias, tolerant alias (a diacritic collision becomes AMBIGUOUS), canonical label of unknown language. Outcomes RESOLVED, AMBIGUOUS, INSUFFICIENT_CONTEXT, UNSUPPORTED, NOT_FOUND, each with reasons, warnings and what context would help. Every candidate carries a grade and evidence (language, alias type, qualification, source origin, evidence eligibility); `operational` is true only for a qualified alias of a runtime-approved source (none exists). Title similarity is never equivalence; only a VERIFIED source-provided EQUIVALENT joins nodes; a conflicting title never overrides an official code (warning `title_conflicts_with_official_code`); seniority is reported as ignored.

## 13. Ambiguity policy (RECOMMENDED OWNER POLICY, pending adoption; implemented conservatively)
Never guess an occupation to produce compensation evidence. Context narrows ONLY through curated `context_terms` stored on aliases (data, not inference); if several candidates remain the result is AMBIGUOUS with the candidates and `context_needed`; if no safe choice exists the result abstains. Unverified alias language gives INSUFFICIENT_CONTEXT unless the caller opts in. No candidate-facing behaviour was activated (D-02 stays open).

## 14. Geography independence and legacy compatibility
Language and country are separate: German text with country DE, CH, AT or none gives the same identity and `country_used` mirrors the input; English never implies a country; an unsupported country is UNSUPPORTED. `LegacyIdentityAdapter` reports, for one legacy id, native code or title: canonical identifier, identity state (linked, ambiguous, unresolved), mapping status, source evidence and relationship qualification; it forces no match and replaces no title-based retrieval. Career AI, Compensation V1, knowledge retrieval, Opportunity workflows and candidate profiles are unchanged.
