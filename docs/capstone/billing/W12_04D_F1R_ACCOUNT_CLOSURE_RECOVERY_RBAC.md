## 1. F1-07 root cause
`POST /auth/account/delete` (self-service) and the privacy-request deletion job both call `AccountDeletionService.delete_account` directly. That service knew nothing about billing: after F1-06 it removed the candidate's provider subscription links and checkout attempts together with the account. A recurring subscription at the provider is independent of those rows, so the provider could keep charging a candidate for whom Ask4Mo held no record, and later events for it quarantined as `checkout_mismatch`. No other path deletes accounts.

## 2. Approved owner decisions
**A.** Subscription-aware account closure. **B.** Dedicated `platform.billing.recover` held by `billing_admin` and `platform_admin` only; billing recovery no longer authorised by `platform.jobs.manage`; fresh step-up required. Both authorised for implementation and offline qualification only.

## 3. Account-closure architecture
Separate obligations, separate fields (never one boolean): (A) closure requested, (B) subscription resolution, (C) provider cancellation, (D) personal-data erasure. One durable case table `billing_account_closures` (migration `0031`), one ACTIVE case per user (partial unique index), holding **no personal data and no provider identifier** (states, timestamps, a retention basis code, an optional privacy-request reference). `closure.assess` is local and read-only. **Blocking** (self-service closure cannot complete): a link whose state is not terminal (`canceled` and `incomplete_expired` are terminal and only authenticated reconciliation sets them), a state outside the known vocabulary (fail closed, `needs_review`), a past-due or unpaid subscription, and a hosted checkout that can still be completed at the provider (blocks until it expires). Scheduled cancellation (`cancel_at_period_end`) is pending, **not** termination. **Permitted:** no subscription, canceled, expired. Normal deletion for users without unresolved billing is unchanged (existing tests pass).
Enforcement at the lowest layer: `AccountDeletionService.delete_account` itself raises `SubscriptionResolutionRequired` when billing is unresolved and `preserve_billing_reference` is not set, so no caller (route, job, future code) can silently orphan a subscription. The route records the case (idempotent; concurrent requests share one case) and answers `409 subscription_resolution_required` with truthful guidance; the account stays intact and signed in. Reconciliation keeps the case in step with verified provider state; when every link is terminal the case becomes `resolved` and the candidate completes closure with the same call, which deletes normally and ends the case (`completed`, account reference cleared, states and timestamps kept as closure evidence).

## 4. Subscription-resolution workflow and provider boundary
States: `requested` (resolution required or unavailable), `awaiting_provider` (cancellation scheduled: waiting for the end), `resolved` (verified terminal), `completed`, `erased_reference_retained`, `withdrawn`, `needs_review`. Provider cancellation: `guided` (the candidate is told to cancel with Link), `confirmed` (only from verified reconciliation), `contract_unverified`; Ask4Mo never requests a cancellation. **PROVIDER CONTRACT VALIDATION REQUIRED:** Stripe's Managed Payments documentation says Link customers cancel or update subscriptions on Link's own site and that Stripe cancels a customer's subscriptions when the customer requests data deletion; whether and how a SELLER may cancel on a candidate's behalf under Managed Payments is not established, so only a fail-closed pending state exists and no provider call is made. With the Null reader the resolution is `unavailable` (reported, never invented); a provider timeout leaves the durable case unchanged; there are no silent retries (the periodic sweep, when enabled, is the reconciliation path). The candidate is never told that future charges have stopped without verified provider evidence (tests scan the copy).

## 5. Privacy and erasure are separate
Account closure and personal-data erasure are different operations; an unresolved provider subscription never postpones a valid erasure. The privacy-request deletion path (`run_account_delete`) calls `ClosureService.begin_retained_erasure` first: with unresolved billing, **all personal and content data is erased** and only the minimum billing reference is retained: an anonymised account shell (`deletion_requested`, provider `closed`, no email, name, credentials or sessions, cannot sign in), the subscription links and their checkout attempts (opaque ids and states only) and the entitlement decision rows. The case records `erasure_status = restricted`, `retention_basis = unresolved_provider_obligation`, `review_required = true` and the privacy request reference (the privacy request's own result category vocabulary is unchanged: the restriction disposition lives on the closure record). When reconciliation shows every subscription terminal the shell, links and checkouts are purged automatically (`completed`, `erasure_status = fulfilled`). Interview histories, resumes, coaching content and memory are never retained because of billing. **No retention period is invented.**

## 6. Dedicated recovery permission
`platform.billing.recover` joins the canonical registry (**44** permissions: the original 43 plus this one). Roles: `platform_admin` (owns all) and `billing_admin` (now 11 permissions). Not granted to `operations_admin`, `support_operator`, `knowledge_admin`, `security_privacy_admin`, candidates or anyone else; `billing_admin` still has no secret-rotation permission and no `platform.jobs.manage`. The three recovery routes (retry, requeue of an expired lease, manual reconcile) now require `platform.billing.recover` **and** a fresh password step-up of the current session (the existing `StepUpService`; no second mechanism). Because the existing step-up routes require `platform.users.role.assign` (owner only), billing-scoped routes `GET/POST /admin/billing/operations/step-up` (permission `platform.billing.recover`) reuse the same service, so a billing admin can elevate. Step-up is password re-authentication, not MFA: an OIDC-only (Google-only) administrator fails closed (`step_up_unavailable`) and cannot recover until a local password credential or an approved OIDC re-authentication exists (documented limitation). Reason, Idempotency-Key, record-state validation, environment validation, concurrency protection, same-transaction audit and the refusal with the Null reader are unchanged; recovery still cannot refund, reprice, grant or forge.

## 7. Generic job-API bypass protection
`platform.jobs.manage` could retry a failed `billing_process_provider_event` job through `POST /admin/jobs/{id}/retry`, which re-drives provider billing processing. Both provider-billing job types now have `manual_retry = False`: the generic retry is refused (409) for them and billing recovery is the only human path. Neither type is Admin-enqueueable. Generic cancel of a queued job only delays processing (the stored event is the outbox and the sweep recovers it) and was left unchanged. Background workers still run through the trusted service-execution boundary, never as an administrator. An operations admin gets 403 on every billing recovery route.
