## 2. Pipeline and what is deliberately NOT collapsed
```
Stripe -> POST /api/v1/billing/webhooks/stripe -> raw-body signature verification -> environment + structure validation
       -> DURABLE acceptance (billing_provider_events)      <-- the HTTP acknowledgement is sent only after this commit
       -> idempotent claim under a lease (job or sweep)
       -> provider-state reader (the provider's CURRENT truth)  ->  ownership / price / environment / stale / terminal guards
       -> verified local link (billing_provider_links; checkout, payment, subscription, refund, dispute are SEPARATE columns)
       -> entitlement decision under an EXPLICIT policy (entitlement_bridge) -> subscriptions row source="provider"
```
Authentication, acceptance, storage, reconciliation, subscription state and entitlement are six separate steps; the route changes no entitlement and the bridge never sees a webhook.

## 3. Official Stripe contracts reviewed (and what is uncertain)
Reviewed from Stripe's documentation (webhooks, subscription webhooks, Managed Payments): the `Stripe-Signature` header (`t=` plus one or more `v1=` HMACs over `<t>.<raw body>`, several while a secret is rolled); event ids identify duplicate deliveries; `created` has one-second resolution, equal timestamps happen and it must not decide order; **delivery order is not guaranteed**; live retries for up to three days with exponential back-off, a sandbox retries three times within hours; after `invoice.paid` retrieve the subscription and require `active` before extending access; `canceled` and `unpaid` are the documented revocation states and `canceled` is final; refund and dispute events need a payment-intent to invoice to subscription lookup (API 2025-03-31.basil or later: `InvoicePayment` list, then `invoice.parent.subscription_details.subscription`); Managed Payments supports Billing subscriptions, handles disputes and support itself, and does not support Connect.
**Unconfirmed and therefore not relied on:** `refund.created`/`refund.updated` parity under Managed Payments (the documented subscription refund signal `charge.refunded` is used instead); sandbox availability of Managed Payments events for the owner's account; exact API version a registered endpoint will carry (events are accepted only at the pinned `2026-09-30.endive`, others are recorded as ignored).

## 4. Webhook route
`POST /api/v1/billing/webhooks/stripe`: POST only (GET is 405), no candidate login, no CSRF token (no session exists to forge), no CORS-dependent behaviour, per-IP rate limit, explicit 256 KiB body limit enforced both on `Content-Length` and while streaming, work done off the event loop. Responses contain no payload, signature, secret or internal reason: `200 {"status":"accepted"}`, `400 Webhook rejected.`, `413`, `503 Webhook is not available.` (the category is audited, not returned). It is **non-operational** while `policy.STRIPE_WEBHOOK_AUTHORIZED` is False (code constant: no setting, startup or Admin action flips it), when the billing mode is not Stripe Managed Payments in the sandbox environment, or when no signing secret exists.

## 5. Signature verification and the SecretStore
The unmodified raw bytes are verified with the Stripe SDK scheme (`WebhookSignature`), after our own check of the header: a missing header, malformed timestamp, missing `v1` value, tampered body, wrong secret, **expired and future** timestamps (the SDK alone only rejects the past; tolerance 300 s both ways) are all rejected with nothing stored. The signing secret is read through the W12.4B SecretStore slot of the **configured environment only** (`STRIPE_SANDBOX_WEBHOOK_SECRET` / `STRIPE_LIVE_WEBHOOK_SECRET`; `stripe_provider.webhook_signing_secrets`); a sandbox secret never verifies a live endpoint and vice versa; there is no fallback key and no unmanaged store. Secrets and signatures are never logged, audited or returned.

## 6. Secret rotation
The existing architecture has **one webhook slot per environment**, so an old/new overlap slot would be new infrastructure. It is not needed: when a signing secret is rolled in the Stripe Dashboard, Stripe signs with both secrets for the roll window and the header carries two `v1` signatures, so the one stored (new) secret verifies it; an old-only signature is rejected once the secret is replaced (both tested). Operator steps: roll in Stripe, replace the credential in Admin (step-up, `platform.integrations.secret.rotate`), then restart the API (credential changes are picked up on restart). No permanent fallback secret exists.

## 7. Environment separation
The event's `livemode` must equal the configured environment; a valid signature never bypasses it (sandbox event at a live deployment, live event at a sandbox one, or an unknown environment are all refused). Live is additionally refused outright (`LIVE_BILLING_ENABLED` is False). Event ids are unique per `(provider, environment, event id)`; links are unique per `(provider, environment, subscription id)`; the provider-state snapshot's `livemode` must match too. An event carrying an `account` (Connect context, unsupported by Managed Payments) is recorded as ignored.

## 8. Event allow-list
Processed (14): `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `customer.subscription.created|updated|deleted|paused|resumed`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `charge.refunded`, `charge.dispute.created|closed`. Everything else (including `refund.created/updated`, `radar.early_fraud_warning.created`, `customer.updated`, `invoice.created/finalized/upcoming`, `payment_intent.*`, `subscription_schedule.*`, `entitlements.*`) is stored as **ignored** with a safe category, acknowledged, never reconciled, never grants access. Do not subscribe an endpoint to more than the 14.

## 9. Durable acceptance, idempotency, duplicates
`billing_provider_events` stores only allow-listed normalised fields (ids, status words, integer amounts): no raw body, signature, email, name, address, card data, description or metadata. Unique `(provider, environment, provider_event_id)`; a duplicate (sequential or a concurrent race, tested with 8 threads) returns the stored record and creates nothing. Redelivery after processing is a no-op, two different events for the same business change converge on **one** link, **one** provider subscription row and **one** applied decision, and distinct legitimate updates that share an object id and type (for example repeated `customer.subscription.updated`) are all applied because **reconciliation, not event identity, is authoritative**. A storage failure is a retryable `503`, never an acknowledgement; if only the follow-up job enqueue fails the stored event is the outbox and the sweep recovers it.

## 10. Background processing and crash recovery
Reuses the W10.9 jobs: `billing_process_provider_event` (id-only payload, idempotency key per event, 5 attempts, back-off) and `billing_provider_reconcile` (bounded sweep). The event row is itself the outbox: processing is claimed with one conditional `UPDATE` (status `received`/`failed`, or an expired lease) that sets a 120 s lease and increments `attempt_count`; a worker that dies mid-run loses the lease and the sweep re-claims it; a failure in the work transaction rolls back **everything** (link, subscription row, decision, tested by crashing after the bridge ran and before commit) and records a bounded category with its own exponential back-off (`next_attempt_at`); after 6 attempts the event becomes `needs_review` (operator-visible, never an infinite loop). Quarantined events (`unknown_ownership`, `checkout_mismatch`, `customer_rebind`, `price_mismatch`, ...) change nothing and are visible by status and category. Audit writes happen after commit and are best effort, so an audit failure can never change a billing outcome; the evidence also lives in the event row, the link and the decision table.

## 11. Ordering, provider-state reader and reconciliation
Never trust arrival order or the event body for state. The reader (`ProviderStateReader`: `get_subscription`, `checkout_session`, `checkout_for_subscription`, `subscription_for_payment`) returns the provider's current truth; `FakeStateReader` is the deterministic test double, `NullStateReader` is the runtime default (every read is "not enabled", retryable, never a state) and `StripeStateReader` (official SDK, per-client key, no retries, bounded error categories) is implemented but **never constructed** in this wave. Provider unavailable/rate limited -> retry; not found -> quarantine; incomplete or multi-item answer -> `needs_review`; **a failed read is never read as payment.**
Guards: environment of the snapshot; known provider state; a snapshot **older than the last applied one never overwrites** it; `canceled` and `incomplete_expired` are terminal (a later "active" reading is refused and flagged, not believed); refund state only moves none -> partial -> full and a lost dispute never reverts; a stale event whose implication differs from the provider state is applied as the provider state and the difference is recorded (`event_superseded_by_provider_state`). Tested: invoice.paid before subscription.created, updated before created with equal timestamps, stale failure after recovery, stale `deleted` after active, lagging snapshot, refund before the invoice update, payment failure then recovery, missed webhook recovered by the sweep, unknown subscription, duplicate external subscription.
Periodic reconciliation (`sweep`): re-claims due/abandoned events; refreshes non-terminal links not observed for 24 h; looks up open checkouts that have a provider session, a browser return or are older than 15 minutes and have no link. It is mockable and **polling is not enabled** (no scheduler enqueues the job and no credentials exist). Suggested cadence once validated: one sweep every 15 to 60 minutes; no high-frequency polling.

## 11a. Cancellation is final for ONE provider subscription id only
`canceled` (and `incomplete_expired`) is terminal for **that provider subscription's link**: a later "active" reading or stale event for the same subscription id is refused and flagged `terminal_reactivation_refused`. It never blocks the candidate from buying again: a new purchase gets a new provider subscription id, is bound through its own trusted checkout record and is granted normally, while the old link stays canceled and a late event for the old subscription can neither revoke the newer grant (revocation only ends the assignment created by that very link) nor reactivate it. To stop double charging, checkout creation refuses (409) while the candidate has a LIVE provider subscription, and a checkout already consumed by a subscription is expired so its session can never be reused. Cross-candidate reassignment stays forbidden (customer rebind, customer swap, checkout mismatch and ownership ambiguity are all quarantined). All tested.

## 12. Ownership, normalised lifecycle and persistence
A provider subscription binds to a candidate **only** through the trusted W12.4D-C checkout record: the provider's checkout session for the subscription must carry our `client_reference_id`, that checkout must exist in the same environment with the **same provider session id**, the subscription's price must equal the checkout's mapped price, and currency, interval and amount must equal the immutable commercial terms. An email address is never used. One provider customer maps to one candidate for ever; a customer swap on a bound subscription is refused; a second live subscription for the same candidate is quarantined (partial unique index). Event metadata cannot override ownership (tested).
Tables (migration `0029_provider_webhooks`, additive): `billing_provider_events` (outbox/evidence), `billing_provider_links` (verified binding + provider state, invoice, refund and dispute facts as **separate columns**, cancel-at-period-end, last observation, entitlement decision), `billing_entitlement_decisions` (append-only evidence of every evaluation). The one constraint change: `subscriptions.source` also accepts `provider` (written only by the bridge); `system_default`, `migration` and `admin` keep their meaning, and no existing account is converted. Upgrade from `0028` (existing subscriptions and their partial unique indexes are preserved, tested), and downgrade and re-upgrade on an empty provider surface are tested. **The downgrade is FAIL CLOSED:** it refuses (and deletes nothing) while any row exists in `billing_provider_events`, `billing_provider_links`, `billing_entitlement_decisions` or any `subscriptions` row has `source = 'provider'`, because that data is the only record of verified financial and entitlement history; an operator must back up, export and deliberately clear it first (section 19). Candidate status view: `lifecycle.from_verified_link` maps verified state to words (`active` only with a paid latest invoice; a scheduled cancellation is `cancel_scheduled`, not canceled).

## 13. Provider-initiated financial actions

Two-person approval stays exactly where it was: seller-initiated refunds and price changes. No seller-initiated refund or cancellation is implemented here.

## 14. Entitlement bridge and the policy approval boundary
`entitlement_bridge.py` is the **only** writer of `source="provider"` subscriptions (a test scans the whole source tree; two evaluators assert it). Inputs: a reconciled link and an `EntitlementPolicy`. Not inputs: client claims, redirect parameters, raw request ids, unverified events, mock flags.
**Policy:** the owner has not approved trial, grace, refund, cancellation, dispute or pricing rules, so `runtime_policy()` is `UNAPPROVED` (always, whatever `PAID_ENTITLEMENT_POLICY_APPROVED` says: approving rules is a reviewed code change that adds a policy, never a setting) and every evaluation records `policy_unapproved` with **no** change. An undecided rule is `None` and yields `hold` (leave access as is, flag it): undecided never grants and never revokes. Offline tests use a clearly named `SYNTHETIC-TEST-POLICY` (never a runtime value, never an approval of any price).
Mechanics: grant = end the candidate's `system_default` row and add a `provider` row on the checkout's plan version (admin and migration assignments are never overridden: `skipped_manual_assignment`); revoke = end only the provider row created by that link and restore the `system_default` Basic row (a manual or newer assignment is never touched); a replay changes nothing and nothing is extended (no expiry exists to extend). Active without a paid invoice, `checkout.session.completed` alone, a redirect, an unverified event and an unknown customer never grant.
