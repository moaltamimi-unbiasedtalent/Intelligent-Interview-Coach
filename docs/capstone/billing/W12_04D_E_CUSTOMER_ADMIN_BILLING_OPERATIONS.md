## 6. Admin API and authorization
`/api/v1/admin/billing/operations/*` (`admin_billing_ops.py`): GET overview, readiness, subscriptions, checkouts, events, events/{ref}, reconciliation, recovery-actions (all `platform.billing.read`: `billing_admin` and `platform_admin`); POST events/{ref}/retry, events/{ref}/requeue, subscriptions/{ref}/reconcile (`platform.jobs.manage`: `operations_admin` and `platform_admin`). **Rationale:** a recovery action re-drives background processing, which is what the existing job-management permission governs; it moves no money. The billing admin can inspect but cannot re-drive; the operations admin can re-drive but cannot see financial diagnostics (so cannot read what it recovers unless also granted). Documented requirement, not implemented: a narrow `platform.billing.recover` permission would let one role do both without broader authority; it was **not** added (the registry stays at 43, no role was broadened). `billing_admin` still cannot rotate Stripe secrets (owner only, with step-up) and `support_operator` has neither permission; candidates get 403. All verified over real HTTP across every persona.

## 7. Controlled recovery
Three bounded actions on OUR record ids (never a caller-supplied provider id): **retry** (a `failed`, `needs_review` or `quarantined` event), **requeue** (only an event whose processing lease has EXPIRED) and **reconcile** (one stored subscription link). Each requires a reason (5 to 300 plain characters) and an `Idempotency-Key` (a replay returns the stored outcome and runs nothing); is rate limited; refuses unknown, wrong-environment or wrong-state targets; is concurrency-safe (conditional updates plus the existing claim); records actor, reason, previous status, outcome and a bounded result category in `billing_recovery_actions` and writes the admin audit row (`admin.billing_recovery`) **in the same transaction**. A retry gives a bounded number of extra attempts (`attempt_limit` rises by 3, at most 3 operator retries per event) **without** erasing `attempt_count`, and then runs the event through the **same** claim, provider-state reader, ownership and price guards and entitlement policy as any event. **With the runtime Null reader every action is refused (`reader_unavailable`), never reported as success, and nothing changes.** The actions cannot forge an event, edit a payment status, delete evidence, grant Premium (the bridge acts only under the unapproved runtime policy), or run a refund, payment, purchase or price change. A provider outage during recovery is a recorded failure, and a lagging read cannot overwrite newer state. Provider-initiated refunds, cancellations and disputes remain facts recorded without any Ask4Mo approval; two-person approval for price changes and seller refunds is untouched (tests: no approval or refund row is ever created by recovery).

## 8. Scheduling boundary
`billing/scheduler.py`: a stateless, one-shot, idempotent `schedule_tick` that enqueues the existing bounded `billing_provider_reconcile` job once per 15-minute time bucket (a job in any state for that bucket blocks a duplicate; concurrent scheduler instances create one job). Run as `python -m src.billing.scheduler` from any scheduler; no resident loop, so shutdown is safe; leases, retries, back-off, failure visibility and provider-outage tolerance are the job system's and the sweep's. **Disabled by default** (`RECONCILE_SCHEDULER_ENABLED = False`) and it additionally refuses while the runtime reader is the Null reader. Nothing is scheduled today and no Stripe polling is authorised. Suggested cadence once validated: 15 to 60 minutes.

## 9. Audit, privacy and retention
Audit: `admin.billing_recovery` (same transaction as the outcome), `admin.billing_event_viewed`, plus the W12.4D-D `billing.*` processing events and `billing.recovery_*` records; no secret, payload or personal data; correlated by ids. Privacy: the operations surface exposes counts, ids, masked provider ids and status words only; no candidate content exists in any billing table. Retention: verified events, links, decisions and recovery actions are financial and audit evidence and are never deleted to clear a warning; the downgrade of `0029` and `0030` is fail closed. **Provider-initiated deletion:** per Stripe, when a Link customer requests deletion Stripe cancels their subscriptions and deletes their data from the Managed Payments objects; Ask4Mo would then receive a cancellation event and record it (the local link is retained as a financial fact holding only opaque ids, no personal data). Candidate account deletion removes the candidate's checkout attempts and links by cascade. **Unresolved owner/legal decisions (no period invented):** how long events, links, decisions and recovery records are retained, and how Ask4Mo should treat retained opaque references after a provider-side deletion.
