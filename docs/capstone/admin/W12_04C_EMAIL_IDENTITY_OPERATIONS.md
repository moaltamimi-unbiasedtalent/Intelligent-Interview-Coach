## 2. Findings and what was done
| # | Finding | Action |
|---|---|---|
| 1 | The submission result was a `bool` that nobody read: a provider failure looked identical to success and nothing was recorded | `EmailService` boundary returns a bounded `SendResult` (status, failure category, provider message reference); one `EmailAttempt` row per submission; a failure writes a category-only audit event |
| 2 | **Token consumption was not atomic** (read, then write): two concurrent redemptions could both succeed | one conditional `UPDATE ... WHERE consumed_at IS NULL AND expires_at > now`; a 12-thread test proves exactly one winner |
| 3 | **Pre-hijack:** an attacker registers a victim's address with their own password; when the real owner later signs in with Google (verified email) the identity was linked into the attacker's account | when linking onto an account whose email was never verified, its password credential, sessions and pending links are destroyed first; a verified account keeps its password; an unverified Google email never links |
| 4 | The console adapter printed verification and reset links (tokens) to stdout in hosted environments | console is development/test only; staging and production use `NotConfiguredEmailSender` (prints nothing, reports `not_configured`) |
| 5 | Password reset was offered to OIDC-only and deactivated accounts | a link is issued only to an ACTIVE account that has a password credential; the public answer is identical in every case (audit records the branch). Whether OIDC-only users should be able to SET a password is a product decision, left open |
| 6 | Older verification or reset links stayed valid after a new one was issued | issuing retires earlier unused links of that purpose (newest wins) |
| 7 | Email was English only | eight-locale templates (the recipient's interface language; English fallback) |
| 8 | A rejected, expired or already-used link all read the same | stable codes `token_invalid`, `token_used`, `token_expired` (shown only to the holder of the 256-bit token) mapped to localised copy |
| 9 | Resend had an hourly ceiling only | plus a 60 second per-account cooldown (429), and an honest 503 `email_unavailable` for the signed-in owner when the provider fails |
| 10 | Production did not require an HTTPS link origin | `APP_BASE_URL` must be `https://` in production (links are built from this configured origin only, never the Host header) |
| 11 | No Admin visibility, probe or test | delivery diagnostics, a read-only connection probe and a bounded test email (below) |

## 3. Brevo integration
- **Real transactional sends:** yes (existing real HTTPS adapter, retained, not rewritten). Endpoint `https://api.brevo.com/v3/smtp/email`, 10 second timeout, no redirects, **no automatic retry**.
- **Outcomes** are reduced to bounded categories: `provider_accepted`, `failed` with `provider_auth_failed`, `invalid_sender`, `message_rejected`, `rate_limited`, `provider_unavailable`, `provider_timeout` (never reached the provider), and `delivery_unknown` (a read timeout AFTER the request was sent: the outcome is unknown, so it is neither retried nor called failed). The provider's response text is never stored, logged or returned.
- **Credential:** resolved through the W12.4B reader (Admin-managed encrypted credential, then environment, then not configured; never copied). The client is built once per process, so a rotated credential reaches it only after the API **and the worker** restart. Admin shows "Credential saved, provider client restart required, connection not yet revalidated" by comparing the running client with the credential that resolves now; it never calls an unrotated client active.
- **Sender:** `EMAIL_SENDER` is deployment configuration (never user input, no CR/LF, `<>`, comma or space). A configured sender is not a verified sender: the connection probe makes two read-only GETs (`/v3/account`, `/v3/senders`) and passes only if the credential authenticates AND the sender is an active Brevo sender. It sends no email. Verification is reported as "verified at the last connection test", never as standing fact.
- **Non-secret settings** (`EMAIL_PROVIDER`, `EMAIL_SENDER`, `APP_BASE_URL`) stay environment-managed (W12.4F).

## 4. Delivery states (what is and is not claimed)
Provider status is not delivery status. The only states are: not configured, configured not tested, connection test passed, **provider accepted a submission**, submission failed (with a category), outcome unknown. **No `delivered` or `bounced` state exists** in the data model, the API or the UI, because no delivery event is collected.
- **Webhooks: not implemented, by decision.** Trustworthy delivery events need a public, provider-authenticated, replay-safe, idempotent endpoint bound to known messages; that is a separate security surface and was not safe to add within this bounded wave. Brevo provides transactional event webhooks, so a later wave can add them; until then delivery is never confirmed. This is an explicit limitation, not a capability.

## 6. Journeys
**Registration:** register (optional interface language) -> uniform response -> one verification email -> link `<APP_BASE_URL>/verify-email?token=...` -> single-use redemption -> `email_verified`. Provider acceptance never marks an account verified. States shown: pending, verified, expired, already used, invalid, resend cooldown, provider unavailable (resend only; the public register response stays uniform). **Policy unchanged and documented:** sign-in and normal use do not require a verified email (`test_email_verification_policy`); changing that is a product decision.
**Recovery:** forgot-password -> identical answer for known, unknown, OIDC-only, deactivated and malformed -> one reset email to an eligible account -> single-use link (1 hour) -> new password -> **every session of that account is revoked**, other pending reset links die, OIDC identities and other accounts are untouched -> old password fails, new works. A provider outage is recorded internally (attempt, audit) and never reported publicly; there is exactly one submission per request (no retry loop, no token regeneration storm).
**Token security:** 32 random bytes (about 256 bits), SHA-256 at rest, constant-time comparison, single use enforced by one conditional update, account and purpose bound, expiry 24 hours (verification) and 1 hour (reset), rate limits per IP and account.

## 7. Google / OIDC (corrected after an independent standards review)
**Root cause.** The first review wrongly called the missing ID-token validation and PKCE harmless. The code requested `scope=openid`, so Google's token endpoint returned an `id_token`, and the provider **discarded it** and trusted only a UserInfo call, so OpenID Connect Core 3.1.3.7 (ID-token validation) and 5.3.2 (UserInfo `sub` must match the ID-token `sub`) were not met, and RFC 9700 2.1.1 (authorization-code injection must be prevented by PKCE or an OIDC nonce) was not met either. State alone defends the login-CSRF case, not every injection case, and the BCP asks for PKCE even from confidential clients.
**Now:**
- **PKCE S256:** `start` creates a 64 character random verifier per transaction, stores it in an HttpOnly, SameSite=Lax, 10 minute cookie bound to the initiating browser and sends only the S256 challenge. The callback refuses to redeem a code without the verifier, and the token call sends it with the client secret. State, destination and verifier cookies are all cleared on **every** callback outcome (success or failure), so a transaction is attempted once. A test with a mock Google that enforces PKCE shows a code issued for another browser does not log the victim in.
- **ID-token validation** (`validate_id_token`): authenticity method is TLS validation of our own direct token-endpoint response (OIDC Core 3.1.3.7 step 6 permits this instead of a signature check when the token never passes through the browser); `alg` must be `RS256` (so `none` and HMAC are refused); `iss` is Google's issuer; `aud` contains our client id (several audiences need `azp`, and any `azp` must be ours); `exp` in the future and `iat` neither in the future nor older than a day (60 s skew); `sub` a non-empty string of at most 255 characters; `at_hash` verified when present. The ID token is the authoritative source of the subject; no claim from a failing token is used.
- **UserInfo** supplements only: its `sub` must equal the validated `sub`, and a repeated email must match; any mismatch rejects the sign-in **before** any local account is created or linked.
- **`email_verified`** must be a real boolean (a string or number rejects the sign-in); the stricter of the ID-token and UserInfo values wins; the linking layer links only on a boolean `true`.
- **Redirect URI:** hosted environments use only the configured `OIDC_REDIRECT_URI` (https, ending `/api/v1/auth/oidc/google/callback`); the request Host is never trusted there, and without a valid value the flow returns 503 instead of guessing. Development and test fall back to the request origin. Production validation requires it when `FEATURE_GOOGLE_LOGIN` is on.
- **Nonce:** not added; with PKCE (RFC 9700 allows PKCE or nonce) and a directly obtained ID token it adds no further defence. Local signature verification against Google's keys was not added because the TLS method is the one the specification allows for this flow.
Live Google sign-in remains not validated and is not wired into the candidate sign-in page. Tests: `tests/test_oidc_hardening_w12_4c.py` (78 cases, real provider against a mock Google, no real network).
