## Design and transaction boundary

**No additive migration.** The existing 0048 primary key, durable owner, status, settled bit and deadline suffice. `RunControlStore.claim` uses one conditional UPDATE on run id + owner + status=completed + settled=true, committing running/unsettled before checkpoint mutation. Historical first claims use the unique primary-key INSERT; an insertion conflict refuses rather than bypassing admission. Claims never steal a running, cancelled, expired, failed or unsettled row. No Redis lock or time-based takeover is introduced.

Services check checkpoint ownership before revealing local busy state, acquire a nonblocking local lock as defense in depth, obtain the database claim and re-read the authoritative checkpoint before validating continuation/HITL state. No database transaction or row lock is held during model/tool execution. The producer retains its durable claim through checkpoint completion, actual cumulative usage recording and terminal bookkeeping. SQL finish/Stop transactions determine the outcome; a late Stop/deadline winner is reflected in synchronous responses as well as GET/SSE observations.

Fresh synchronous runs acquire control when the schema supports it, closing the analogous initial-sync settlement window. Historical runs without metadata are adopted after checkpoint ownership verification when 0048 exists; their next mutating checkpoint records control_required. Pre-0048/no-store synchronous behavior remains available under the existing local serialization; it is not a claim of cross-process safety without the control schema. Required control metadata that is missing/unavailable fails closed and is never silently recreated.

Validation-only failures restore a settled, retryable state without changing checkpoint/messages/usage. A concurrent Stop is preserved during that restoration. Once execution may have advanced, interruption leaves the row unsettled and blocks automatic continuation. Usage recording reports success/failure internally rather than swallowing it as settlement success. Failed recording never emits a false settled SSE result. Unknown/incomplete usage projects unavailable cost, never zero; known cumulative checkpoint entries and the existing canonical monotonic guard remain intact. No telemetry schema, pricing, billing reservation, tool permission, entitlement or language activation record changes.

The service also retains the official saver resource context for its lifetime, verified through the default PostgreSQL constructor; otherwise its connection context could be discarded on service creation. The existing Stop regression setup now claims the already-created synchronous control row instead of inserting a duplicate; its assertions are retained.
