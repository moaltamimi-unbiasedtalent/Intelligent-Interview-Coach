## 4. Security and privacy impact
- Authorization is server side only. Matrix tested: non-member 404 on every transfer route; member who is not a party sees `{"transfer": null}` and gets 404 on cancel/decline/accept; the proposer cannot decline, the recipient cannot cancel; the owner of workspace A cannot touch B and vice versa; tokens are bound to ONE account (anyone else gets the same 404 as an unknown token); unverified, deactivated or re-addressed recipients are refused; production returns 401 on all nine routes without a session.
- The token and the recipient address are never stored in clear, never returned, never in a log (asserted with `caplog` at DEBUG), never in an audit row, never in the export. The notice names neither workspace nor proposer. The counterpart is shown by display name or a masked address only.
- Audit rows carry ids, roles, an outcome and a fixed reason code (asserted: no workspace name, no address, no token, no display name).
- A password is held only in the dialog state, sent only to the step-up route, cleared after every attempt, and never stored or audited by this package.
- The step-up proves a password on THIS session; it is not MFA and is not described as such.

## 6. Risks and limits
- PostgreSQL behaviour of the claim statements and the partial unique index was not executed (SQLite only here); the DDL is portable (`postgresql_where` set) and the migration test checks the SQLite rendering.
- A Google-only owner cannot propose (step-up fails closed). A password-less staging or production account is therefore unable to transfer ownership today.
- Acceptance depends on the emailed link. No live email was sent; delivery is `submitted` at best and was never observed in a real mailbox. If the notice is lost the proposer must cancel and propose again.
- Expired rows are marked expired lazily (on a read, a decision or a new proposal), not by a background job.
- Archive keeps a pending transfer alive (acceptance refused until restored).
- Existing browser sessions hold the old UI until reload; there is no API-compat shim for the removed one-step route (the only caller was the previous frontend).
