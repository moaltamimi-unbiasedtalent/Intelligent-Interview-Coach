### Decisions taken (and why)
- Roles stay plain strings in the existing `String(24)` column: `workspace_owner`, new `workspace_admin`, `workspace_member`. No migration needed.
- **No migration was needed for anything in scope.** Archive reuses the stored status `deactivated` (Platform Admin and the evaluators already filter on it; the candidate UI says "Archived"); consent is recorded as the grant `created_at` plus the audit event; transfer stays a single owner-initiated, typed-confirmation step (no pending-transfer table). The reserved revision `0044` was NOT used. Alembic head is unchanged (`alembic heads` is whatever the prep branch has; `tests/_alembic_head.py` checks were not touched).
- One deliberate omission caused by the no-migration choice: invitation e-mails are NOT written to the `email_attempts` diagnostics table, because its message-type CHECK (migration 0027) does not list `workspace_invitation` and widening it would need a migration. The mail still goes through `EmailService` (bounded `SendResult`, adapter exceptions contained).

## 4. Security and privacy impact
- Closed: unverified-address invitation takeover (G7), double acceptance (G6), operator enrolment of staff into member workspaces (G13), shares into archived workspaces (G12), stale reads after the sharer left (read now also needs the sharer to be an active member), evidence-link leakage in the shared story projection, retained PII in invitations after account deletion (G14).
- Authorization is server side only: the UI reflects `capabilities` but every route re-checks. A non-member (never joined, invited-not-accepted, left, removed, unverified, member of another workspace) gets 404 on every workspace-scoped route; an active member without the role gets 403.
- No candidate content is visible to workspace owners or admins beyond what members explicitly shared; Platform Admin keeps metadata only (`active_share_count`), cannot read a shared item, and cannot enrol platform staff.
- Invitation tokens are 32 random bytes, stored only as SHA-256, single use, 72 h, never in a response or an audit event. The mail is generic by design (no workspace or inviter name) so user-authored text cannot be used for phishing through it. Recipient address validation rejects header-injection characters.
- Member labels: display name, else a masked address (`m***@x.com`); full addresses only to owner/admin (who invited them) and to the person themselves.
- Audit (existing audit table, no schema change): `workspace.created|renamed|archived|restored|deleted|invite_created|invite_accepted|invite_declined|invite_revoked|member_role_changed|member_removed|member_left|ownership_transferred`, `share.created` (carries `consent` and the visible member count) and `share.revoked`. Contexts hold ids, roles and counts only (asserted: no address, token, workspace name or content).
- Audit writes are best effort (unchanged P6.5 behaviour: an audit failure does not block the action; it now logs a content-free warning).

## 6. Risks and limitations
- SQLite serialises writers, so the race tests cannot prove PostgreSQL behaviour. The code relies on a conditional UPDATE (correct under read committed) and `SELECT ... FOR UPDATE` on the workspace row for membership changes; the FOR UPDATE part is a no-op on SQLite and is NOT exercised by any test.
- Ownership transfer is the minimal safe default (immediate, typed confirmation, to an active member). OD-WS-TRANSFER is unresolved; a cooling-off or a recipient-acceptance step would need a pending-transfer table (a migration).
- Invitation sends are not recorded in the Admin e-mail diagnostics (CHECK constraint, see section 1). `submitted` means the provider accepted the message, never delivery (no webhook exists).
- Accessibility is covered by semantic markup, labelled controls, alert dialogs with safe initial focus, vitest and Playwright assertions of roles and names, and a Playwright Escape/focus test. There is no automated axe/contrast run and no screen-reader test; no WCAG claim is made.
- Archiving revokes every grant and a restore never revives one: members must consent again. This is intentional (consent must not silently reappear) and may surprise users; the copy says so.
- The platform-staff enrolment guard stops staff accounts only. An operator can still enrol an ordinary account; that account then reads what members shared. Closing that fully would mean removing Admin member enrolment or requiring the workspace owner's consent (owner decision).
- Existing grants into a workspace stay readable for every member who joins LATER (a grant is to the workspace, as designed and as the consent text says).
- The new copy is an engineering translation pending native review.
