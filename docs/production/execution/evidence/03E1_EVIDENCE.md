## Design decisions (documented in the module docstring of `src/reporting/report_builder.py`)
- Two route families, one per EXISTING read permission, mirroring W10.12: `/admin/report-builder/*` (`platform.reports.read`) and `/admin/report-builder/commercial/*` (`platform.reports.commercial.read`). 10 routes each, 20 total. No new permission (registry stays 44). A report type of the other family is 403, never trimmed.
- Reads stay GET: validate and preview take the definition as query parameters (no read POST, so the audit-coverage invariant needed no loosening). Export is a POST on purpose (like the audit export) because it writes an audit row.
- Windows: builder maximum is 90d; `all_time` is refused as over-wide (`window_too_wide`) but stays on the fixed `/admin/reports/*`.
- Cohort rule (tested): figures come only from the existing suppressed pipeline; a filter selects ROWS after primary and secondary suppression, must name the grouping dimension (`cross_dimension_filter` refused, `filter_needs_grouping` refused). Hence any filtered or saved variant shows only cells the unfiltered grouped preview already shows, and a suppressed bucket stays suppressed under every filter subset (exhaustively tested). Previous-period comparison re-runs the same pipeline one window earlier (disjoint, equally suppressed). Mock MRR/ARR must be grouped by currency (currencies never combined).
- Sharing: a saved configuration is private to its owner; `shared` lets other Admins who already hold the report's read permission view and run it (re-validated under the viewer's permissions). They cannot edit or delete it. No new permission.
- Saved configurations: owner-scoped (FK users CASCADE), unique name per owner, 25 per owner, definition at most 2048 bytes, validated names, `expected_revision` compare-and-swap on update and delete (query parameter on DELETE), identical repeat of an update or create is an idempotent no-op, stored definitions are re-parsed and re-validated on every read or run (a corrupted row lists as `valid: false`, runs as 422). Audit in the same transaction (`admin.report_config_created|updated|deleted`; ids, report type, revision, changed field names only).
- Exports: at most 2000 rows (over the limit is refused, never truncated), formula-injection-safe (`= + - @`, tab, leading-space variants get an apostrophe, control characters dropped, numbers untouched), filename built only from registry slug, window and format, `Cache-Control: no-store`, CSV streamed. Audited BEFORE sending with who, report type, window, format, row count, grouping, saved id; if the audit write fails nothing is exported (503). Synchronous because the result is bounded aggregates; the W10.9 job pattern was not needed.

## Security and privacy impact
Aggregates only; no identifier, e-mail, owner id or candidate content in any response (banned-key and sentinel sweeps over every GET, allowlist `extra=forbid` schemas, no `Any`/dict). No provider, network, job or write to candidate data. Saved rows hold definitions only (column set asserted). 7-persona 403 matrix for all 20 routes (derived from the presets), anonymous refused, deactivated Admin refused, cross-owner isolation (404 for private, 403 for edit of a shared one). Residual limitation, unchanged from W10.12 and documented: nested fixed windows and a total against buckets with two or more hidden buckets can be subtracted by a reader allowed to read both; the builder adds no window, grain or dimension beyond `/admin/reports/*`. REPORTING_MIN_COHORT is an engineering control, not anonymisation.

## Remaining risks and limitations
- Feedback is the only metric the builder computes itself; its figure is the count of feedback items (03K definition) and differs from the legacy W10.12 `feedback_total` (distinct candidates), which is not exposed by the builder.
- Metric values come from the legacy suppressed figures, so the builder does not return numerator or denominator (exposing them would leak cohorts); `unavailable` and `not_captured` are normalised to the metric's 03K `missing_behaviour` (`unavailable`) with the original state in the note.
- The per-owner count limit is checked in the same transaction but not under a database lock; two simultaneous creates at the limit could exceed it by one on PostgreSQL.
- No frontend (03E2). No Playwright (backend only; port 3107 unused).
- OD-REPORT-EXPORT (final format set) and scheduled distribution (R1.2) are open owner items.
