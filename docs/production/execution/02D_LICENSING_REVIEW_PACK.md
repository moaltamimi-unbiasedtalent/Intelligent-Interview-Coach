## 0. Plain statement of status (read first)
- **NOTHING IS APPROVED.** No source is approved for any market. The approval register (`docs/production/execution/source_approval_register.json`) is committed EMPTY and a test asserts it. Engineering never approves a source and never writes a record into the register.
- **The only evidence in this pack is the repository.** Every fact below is read from files committed in this repository (the source manifest, the generated source status snapshot, the coverage matrix, the P10C-F1 source dossier and register, the governed datasets, the source code). No network call and no web fetch was made while preparing this pack. Licence texts quoted here are the strings RECORDED in the repository; nobody has re-read the publishers' current terms for this pack.
- **The P10C-F1 dossier is earlier engineering research, not legal verification.** Where it says a statement was "found" or "corroborated against the publisher", that was an engineering reading of a web page at that time. It is a starting point for the reviewer, never an approval, and its own header says verification is not approval.
- **Nothing in this pack is legal advice.** Questions below are questions for the qualified reviewer, not conclusions.
- Consequence today: in staging and production the Candidate retrieval filter (PR 1, `src/knowledge_approval.py`) refuses every source for every market, so a Candidate receives no curated or governed knowledge evidence. Development and test label the same sources UNQUALIFIED.

## 1. What the reviewer's decision controls (how an approval takes effect)
1. The reviewer fills ONE approval record per `(source, market)` pair (template in section 8) and returns it to the owner with the evidence reference.
2. The owner (or an engineer acting on the owner's written instruction) commits the record into `docs/production/execution/source_approval_register.json` in a reviewed pull request. An approval has no other path: no setting, environment variable, Admin screen or database row can enable a source.
3. The validator (`src/knowledge_approval.py`) enables the pair only if the record is complete, the approver is a named human, the date is not in the future, the release SHA is well formed, `valid_until` has not passed and is within 366 days of the approval, the licence class is one that can be enabled (never `unclear` or `restricted`), the authority tier equals the manifest tier, and the `enabled` claim agrees. Anything else fails closed.
4. The licence register consistency check also requires that, when a record enables a source the manifest still marks `licence_review_required`, the manifest entry carries the review outcome in the same change.
5. The decision is per market. A record for Germany does not enable the same source for France. A source published in the United States is refused for any non-US market even with a record, until the owner decides OD-US-CONTENT and the code constant `US_GENERAL_INFORMATION_DECIDED` is changed in a reviewed change.
6. The beta-scope coverage measure (02E) reads the same register through `knowledge_approval.beta_scope_view()`, so approving a pair is also what puts it in the measured beta scope.

### 2.2 Administrator-governed uploads
Administrators can upload documents (`src/knowledge_admin`); each carries a licence class chosen from `public_official`, `explicit_permissive`, `internal_owned`, `permission_recorded`, `unclear`, `restricted` (only the first four can be activated), provenance and a malware-scan result, and needs a human approval and an explicit activation. None are present in the repository (they live in the deployment database). Under 02D each such source is identified as `governed:<knowledge_source_id>` and also needs a market record. Whether the Admin-recorded licence class is an adequate basis for a market record is Question Q-14.

## 3. What is stored and what is shown to candidates (as visible in the code)
- Stored locally (never committed): structured SQLite stores (roles, compensation, competencies, labour market, credentials) and a vector collection built from the acquired files. Raw archives live under `data/raw` (git-ignored).
- Shown to candidates: evidence items from those stores, each carrying `source_id`, `source_title`, `source_url`, `publisher`, authority tier, geography or country, reference year and version; text is a rendered record (for example a pay statistic with its pay period and year, a list of tasks or skills for an occupation, a forecast figure) or a narrative passage (chunk) of an acquired document. Candidates see the source title and link as a citation.
- The evidence model has NO licence, attribution or rights-holder field (`src/copilot/models.py`, `KnowledgeEvidence`). Whether the attribution an obligation requires (section 4) is currently displayed to Candidates is therefore an open question for the reviewer and for engineering (Q-9). Nothing in this pack asserts attribution is shown.
- Candidate-facing answers synthesise over this evidence with a language model (OpenRouter, provider abstraction in `src/llm`); whether model synthesis over a source is a use the licence allows is Q-10.
- Nothing is redistributed as a download or an API; Candidates cannot export knowledge records (the export features cover their own data).

## 7. Checklist for the qualified licensing reviewer
For each `(source, market)` you are asked to approve:
1. Identify the source (`source_id` from section 2) and the market (one of IE, DE, ES, IT, PT, FR, NL; EU, UK and US exist as markets in the register but are outside this pack's seven).
2. Read the publisher's CURRENT licence or terms yourself (this pack records strings only). Record the exact page or document you relied on and its date in `licence_terms_reference`.
3. Classify the licence into one register class: `public_official`, `explicit_permissive`, `internal_owned` or `permission_recorded`. If the answer is "unclear" or "restricted", do NOT fill a record: report the question instead.
4. Name the rights holder.
5. Confirm the authority tier equals the manifest tier for that source (the validator refuses a mismatch).
6. Decide which features the source may serve for that market: `role_definition`, `compensation`, `labour_outlook`, `entry_education`, `licence`, `certification`.
7. Write a coverage statement that is true for THAT market: what the source covers there, in which language, for which year, and what it does not cover. Do not claim national coverage from an EU-level source.
8. Confirm attribution and redistribution conditions are satisfied by the product as built (see Q-9, Q-10); if a code change is needed first (an attribution field, a licence notice), record it as a condition and do not approve until it ships.
9. Confirm the source is not a synthetic fixture and is not a US-published source for a non-US market unless the owner has recorded the OD-US-CONTENT decision.
10. Set `valid_until` no later than 366 days after the approval date; choose a shorter period where the publisher's terms or edition change sooner. A passed `valid_until` disables the pair automatically.
11. Sign with your own name (a person; a team, role title, tool or automation label is rejected), the approval date, an evidence reference that lets someone else find your working papers, and the release SHA of the repository state you reviewed (`git rev-parse HEAD` of the commit the owner gives you).
12. Sign off per market. Approval of one market is not approval of another.
13. If the manifest still marks the source `licence_review_required` or lacks a licence string, ask for the manifest entry to carry your outcome in the same change (the consistency check requires it).
14. Never approve on the strength of this pack alone.

## 8. The exact approval record template
Copy one object into the `records` array of `docs/production/execution/source_approval_register.json`, replacing every placeholder. The same object is committed at `docs/production/execution/02D_approval_record_template.json` (a test asserts that the template, unfilled, enables nothing). Field order is not significant; unknown fields make the record invalid.

```json
{
  "source_id": "<REPLACE: manifest source id, or governed:<knowledge_source_id>>",
  "market": "<REPLACE: one of IE, DE, ES, IT, PT, FR, NL, UK, US, EU>",
  "licence_class": "<REPLACE: public_official | explicit_permissive | internal_owned | permission_recorded>",
  "licence_terms_reference": "<REPLACE: the exact page or document and date the terms were read>",
  "rights_holder": "<REPLACE: named rights holder>",
  "authority_tier": 0,
  "coverage_statement": "<REPLACE: what this source covers for THIS market, language and year, and what it does not>",
  "features": [
    "<REPLACE: one or more of role_definition, compensation, labour_outlook, entry_education, licence, certification>"
  ],
  "approver": "<REPLACE: the reviewer's own name, a person>",
  "approved_on": "<REPLACE: YYYY-MM-DD>",
  "evidence_reference": "<REPLACE: where the reviewer's working papers are>",
  "release_sha": "<REPLACE: the repository commit that was reviewed>",
  "staleness_rule": {
    "valid_until": "<REPLACE: YYYY-MM-DD, at most 366 days after approved_on>"
  },
  "enabled": false
}
```

| Field | Meaning and rule enforced by the validator |
|---|---|
| `source_id` | An id from section 2, or `governed:<knowledge_source_id>` for an Administrator-governed source. Unknown manifest ids are invalid. |
| `market` | One of `IE`, `DE`, `ES`, `IT`, `PT`, `FR`, `NL`, `UK`, `US`, `EU`. Upper case. |
| `licence_class` | `public_official`, `explicit_permissive`, `internal_owned` or `permission_recorded`. `unclear` and `restricted` can never be enabled. |
| `licence_terms_reference` | Where the exact terms were read (document or page and date). At least 8 characters, not a placeholder. |
| `rights_holder` | Named rights holder. Not empty or a placeholder. |
| `authority_tier` | 1 official, 2 framework, 3 industry; must equal the manifest tier. |
| `coverage_statement` | True statement of coverage for this market. |
| `features` | Non-empty list of distinct feature names from the list in section 7. |
| `approver` | A named person. Placeholders (TBD, counsel, reviewer, owner and similar) and automation or engineering labels (a tool, bot, script or model name) are rejected. |
| `approved_on` | `YYYY-MM-DD`, not in the future. |
| `evidence_reference` | Where the reviewer's working papers are (at least 8 characters). |
| `release_sha` | 7 to 40 lower-case hex characters: the repository commit reviewed. |
| `staleness_rule` | Exactly `{"valid_until": "YYYY-MM-DD"}`; not passed, and at most 366 days after `approved_on`. |
| `enabled` | A claim that must equal the validated result. Set it to `true` only on a complete record; it can never enable a record by itself. |

After the record is committed: run `pytest tests/test_source_approval_02d.py tests/test_licensing_pack_02d.py`, the consistency check (`knowledge_approval.consistency_problems`) and the beta-scope evaluator; the record is effective on the next process start (the committed file is cached per process).
